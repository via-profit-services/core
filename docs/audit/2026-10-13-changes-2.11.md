## 2. Контекст на каждый запрос

### Что было
```ts
const applicationFactory = props => {
  const context = {};           // ← создаётся ОДИН раз при старте
  const extensions = { ... };   // ← тоже один на всех
  return async (request, response) => { /* все запросы пишут в эти объекты */ };
};
```

### Почему это опасно
Node.js выполняет JavaScript в одном потоке, но **запросы обрабатываются одновременно**. Каждый `await` (запрос к БД, чтение тела) отдаёт управление следующему запросу:

```
время →
запрос A: middleware: context.user = 'alice' ── await БД ──────────── резолвер читает context.user
запрос B:                  middleware: context.user = 'mallory' ──┘   → видит 'mallory'
```

Если объект один, второй запрос перезаписывает данные первого. В PoC запрос alice получил ответ `whoami: "mallory"`. С массивом `validationRule` получилось ещё хуже: middleware из примера в README делал `validationRule.push(...)` на каждом запросе, массив рос бесконечно, и каждый следующий запрос становился медленнее.

**Общее правило:** всё, что зависит от запроса, создаётся внутри обработчика запроса. Снаружи, в фабрике, живёт только то, что одинаково для всех: схема, конфиг, кэши.

### Как исправлено
`src/application.ts`: `context`, `extensions` и копия `validationRule` создаются заново на каждый запрос. Middleware работают как раньше: они мутируют переданный объект, только теперь этот объект свой у каждого запроса. **API не изменился.**

### Обратная совместимость: `sharedContext: true`
Вы писали, что проекты уходят от глобального контекста, но возможность нужно сохранить. Опция `sharedContext: true` включает старое поведение: один объект на все запросы. В типах она помечена `@deprecated` с объяснением риска.

**Когда она нужна.** Только если какой-то middleware рассчитывает, что объект в контексте **переживёт запрос**, например:
```ts
// старый код: пул создаётся при первом запросе и «живёт» в контексте
const dbMiddleware: Middleware = ({ context }) => {
  if (!context.knex) context.knex = createKnex();   // при per-request контексте пул будет создаваться на КАЖДЫЙ запрос!
};
```
**Правильная миграция** (без `sharedContext`): долгоживущий объект создаётся один раз снаружи, а middleware только кладёт ссылку на него:
```ts
const knex = createKnex();                                 // один раз при старте
const dbMiddleware: Middleware = ({ context }) => {
  context.knex = knex;                                     // на каждый запрос: дёшево
};
```
➡️ **Перед обновлением проектов** поищите в их middleware конструкции вида `if (!context.X) context.X = ...`.

**Проверено:** `src/__test__/context.test.ts`. Без исправления 3 из 4 тестов падают; это проверено откатом.

## 3. Загрузка файлов

Это самый большой блок. Ниже разобрано, как устроен протокол, почему старая реализация ломалась и как работает новая.

### 3.1 Как выглядит multipart-запрос

```
Content-Type: multipart/form-data; boundary=XyZ

--XyZ\r\n                                                ← первый разделитель
Content-Disposition: form-data; name="operations"\r\n
\r\n                                                     ← пустая строка = конец заголовков части
{"query":"mutation($f: FileUpload!){ up(f: $f) }","variables":{"f":null}}
\r\n--XyZ\r\n                                            ← разделитель
Content-Disposition: form-data; name="map"\r\n
\r\n
{"0":["variables.f"]}
\r\n--XyZ\r\n
Content-Disposition: form-data; name="0"; filename="photo.png"\r\n
Content-Type: image/png\r\n
\r\n
<двоичные данные файла>
\r\n--XyZ--\r\n                                          ← закрывающий разделитель (два дефиса в конце)
```

Три правила из RFC 2046, на которых всё держится:

1. **Разделитель — это `\r\n--XyZ`, вместе с CRLF.** Этот CRLF принадлежит разделителю, а не данным файла. Поэтому байты `--XyZ` внутри файла разделителем не считаются, если перед ними нет `\r\n`.
2. **Первый разделитель идёт без CRLF перед ним.** Новый парсер просто начинает работу с «виртуального» `\r\n` в буфере, и после этого все разделители выглядят одинаково.
3. **Данные приходят кусками (чанками) произвольного размера.** TCP не знает о структуре multipart: разделитель может прийти разрезанным пополам.

Протокол GraphQL поверх multipart ([graphql-multipart-request-spec](https://github.com/jaydenseric/graphql-multipart-request-spec)): сначала `operations` (запрос с `null` вместо файлов), потом `map` (какой файл в какую переменную подставить), потом сами файлы.

### 3.2 Почему старая реализация ломалась

| Проблема | Механизм |
|----------|----------|
| Файлы портились или запрос зависал | Если разделитель не нашёлся в буфере, **весь** буфер записывался в файл. Когда `\r\n--XyZ` был разрезан между двумя чанками, первая половина уходила в файл, а вторая уже не распознавалась (правило 3) |
| Всё тело запроса оседало в памяти | События `field`/`file` копились в массивах и отдавались только в конце. Данные файлов складывались в `PassThrough`, который никто не читал, то есть в RAM |
| Лимиты не работали | В парсер лимиты не передавались вообще, событие `limit` никто не генерировал. А проверки в обработчиках срабатывали только после того, как всё тело уже прочитано |
| Вечное ожидание | Если файл из `map` не приходил, промис загрузки не завершался никогда, и резолвер висел вместе с соединением |
| Prototype pollution | См. 3.5 |

### 3.3 Как работает новый парсер (`src/utils/Multipart.ts`)

Это **конечный автомат** (state machine). У парсера есть состояние, и каждый новый чанк обрабатывается в зависимости от него:

```
                ┌─────────────────────────────────────────────┐
                ▼                                             │
 preamble ──► after-delimiter ──"\r\n"──► headers ──► body ───┘ (нашли разделитель)
   (ищем                │                (ищем        (ищем
  первый                └──"--"──► done   \r\n\r\n)   разделитель)
 разделитель)
```

**Ключевой приём — «безопасный хвост».** В состоянии `body` парсер ищет разделитель в буфере:
- если нашёл, всё до него — данные части, часть закрывается;
- если не нашёл, отдаёт данные **кроме последних `длина_разделителя − 1` байт**. Эти байты могут оказаться началом разделителя, который придёт следующим чанком. Они остаются в буфере и склеиваются со следующим чанком.

```
чанк 1: ...данные файла ...\r\n--Xy      чанк 2: Z\r\nContent-Disposition...
                           └────┘ хвост: не отдаём, ждём продолжения
склейка: \r\n--XyZ\r\n...  → разделитель найден целиком
```

Тест `a delimiter split at ANY position between two chunks` режет тело запроса **в каждой возможной позиции** (несколько сотен вариантов) и проверяет, что файл приходит байт в байт. Ещё один тест подаёт всё тело **по одному байту**.

**Обратное давление (backpressure).** Данные файла сразу отдаются в `Readable`-поток, который пишется во временный файл. Если диск не успевает:

1. `stream.push(data)` возвращает `false`: внутренний буфер потока полон;
2. парсер **не вызывает** callback своего `_write` и запоминает его;
3. Node видит, что `Writable` не готов принимать данные, и приостанавливает чтение сокета; клиент тоже притормаживает (TCP flow control);
4. когда потребитель читает данные (`_read`), парсер вызывает отложенный callback, и чтение возобновляется.

В итоге память на одну загрузку — это размер буферов потоков (десятки КБ), независимо от размера файла. Тест `backpressure: the parser stops reading while the file is not consumed` проверяет это напрямую: пока файл никто не читает, из 20 МБ вычитано меньше 5 МБ.

**Лимиты проверяются по мере чтения:** размер поля, размер файла, суммарный размер, число файлов, полей, частей и размер заголовков части. При первом нарушении парсер останавливается с ошибкой. В e2e-проверке через настоящий HTTP-сервер клиент начал слать 50 МБ при лимите 1 КБ и получил ответ 400 через 13 мс, успев отправить около 3 МБ.

**Строго CRLF.** Тело с одиночными `\n` теперь отклоняется. Тест 2.1 ожидал обратного, я его изменил. Причина: если принимать `\n--XyZ` как разделитель, двоичный файл с такими байтами будет разрезан. Строгость здесь и есть защита от неоднозначности.

**Прочее.** Boundary в кавычках, регистронезависимый `Content-Type`, `filename*=UTF-8''...` (RFC 5987, кириллические имена), имя файла очищается от пути (`C:\Users\...\a.png` → `a.png`, `../../etc/passwd` → `passwd`). При этом имя файла от клиента **по-прежнему нельзя использовать как путь на сервере**.

### 3.4 Жизненный цикл загрузки (`src/utils/graphql-file-uploader.ts`)

1. `operations` → JSON-объект, `variables` обязаны быть объектом.
2. `map` → для каждого файла создаётся `FileUploadInstance` (промис) и подставляется в `variables` по пути.
3. Каждый файл **сразу пишется во временный файл** с обратным давлением.
4. Тело считается готовым, только когда разобран весь запрос **и** все файлы лежат на диске. Если файл из `map` не пришёл, запрос получает ошибку `File «0» is referenced in the «map» ... but was not received` вместо вечного ожидания.
5. Резолвер получает `FilePayload` как раньше: `createReadStream()`, `fileSize`, `filename`, `mimeType`, `cleanup()`.
6. **Временные файлы удаляются автоматически**, когда закрывается HTTP-ответ (событие `close` у `ServerResponse`). Если реального `response` нет (тесты, вызов без сервера), файлы удаляются после выполнения запроса.

> **Контракт для резолверов:** прочитайте или скопируйте файл до того, как уйдёт ответ. Вызывать `cleanup()` теперь не обязательно, но можно, он идемпотентен. Раньше файлы оставались в `/tmp` навсегда, если резолвер забывал вызвать `cleanup()`.

**При ошибке чтение останавливается, а остаток тела не дочитывается.** В первой версии я вызывал `request.resume()`, чтобы дочитать тело, и тест показал, чем это плохо: при лимите 1 КБ сервер честно скачивал бы все 10 ГБ, которые шлёт атакующий. Теперь ядро просто отсоединяется от потока, а что делать с остатком, решает HTTP-сервер.

**Временный файл** (`src/utils/TempFile.ts`):
- имя — случайный UUID, его нельзя угадать или подставить;
- флаг `wx`: ошибка, если файл уже существует (защита от подложенной симлинки);
- права `0600`: файл может читать только пользователь сервера;
- все операции с ФС асинхронные: `mkdtempSync`/`unlinkSync` блокировали event loop для всех запросов;
- удаление дожидается закрытия потока записи. Иначе возможна гонка: файл удалён раньше, чем асинхронно создан, и остаётся на диске навсегда.

### 3.5 Prototype pollution через `map`

**Что было.** Путь из `map` проверялся оператором `in`:
```ts
if (!(part in current)) return false;
```
Оператор `in` смотрит и в **цепочку прототипов**: `'__proto__' in {}` и `'toString' in {}` оба дают `true`. Путь `variables.__proto__.toString` проходил проверку, после чего `current = Object.prototype` и `Object.prototype.toString = upload`. Это **один объект на весь процесс Node**: после такого запроса `String({})` падает во всех запросах всех пользователей.

**Как исправлено** (`src/utils/map-path.ts`):
- проверка только **собственных** свойств: `Object.prototype.hasOwnProperty.call(obj, key)`;
- сегменты `__proto__`, `constructor`, `prototype` запрещены явно;
- путь обязан начинаться с `variables.`;
- для массивов допускается только целый индекс внутри длины массива.

**Общее правило:** если ключи приходят от клиента, никогда не используйте `in` или `obj[key]` без `hasOwn`, а для словарей из клиентских данных используйте `Object.create(null)` или `Map`.

**Проверено:** 6 вариантов вредоносных путей в `uploads.test.ts`, и после каждого проверяется, что `Object.prototype` не тронут.

### 3.6 Почему свой парсер, а не busboy
В январе 2026 вы сознательно убрали busboy ради нулевых зависимостей, поэтому я сохранил это решение и написал парсер заново. Цена такого решения — ответственность за код парсера. Чтобы она была посильной:
- код подробно прокомментирован (формат, правила, где какая проверка);
- тесты покрывают разрезы в любых позициях, двоичные данные, лимиты, обратное давление, обрывы и порядок частей.

Если когда-нибудь решите вернуть busboy, интерфейс `Multipart` (события `field`/`file`/`finish`/`error`) совместим с ним по смыслу, и `graphql-file-uploader.ts` почти не придётся менять.

### 3.7 Что изменилось для кода проектов
- `FileUploadScalarType` узнаёт загрузку через `Symbol.for(...)` вместо `instanceof`. Пакет поставляется в двух сборках (ESM и CJS), и если приложение загрузит обе, получится два разных класса, на которых `instanceof` ломается.
- `mimeType` — только тип в нижнем регистре, без параметров (`image/png`, а не `Image/PNG; charset=…`).
- `DEFAULT_MAX_FIELD_SIZE` уменьшен с 16 МБ до 1 МБ: поля (`operations`, `map`) держатся в памяти, а для обычных JSON-запросов лимит и так 1 МБ.
- `DEFAULT_MAX_FILE_PARTS` = 26 (20 файлов + 6 полей). Раньше было 20, то есть 20 файлов вместе с `operations` и `map` в лимит не помещались.

## 4. Правила depth и complexity

### 4.1 Экспоненциальное время → мемоизация
**Что было.** Правило глубины заново обходило фрагмент при **каждом** его упоминании:
```graphql
{ ...F0 ...F0 ... (30 раз) }
fragment F0 on Query { ...F1 ...F1 ... (30 раз) }
fragment F1 on Query { ...F2 ... }  # и т.д.
```
Путей обхода получается 30^уровней: запрос в 1 КБ обрабатывался 3,2 секунды. Валидация синхронна, поэтому всё это время сервер не отвечал **никому**.

**Как исправлено.** Применена мемоизация: результат для фрагмента считается один раз и запоминается в `Map`. Повторное упоминание стоит O(1), и правило становится линейным от размера запроса. Сейчас тот же запрос обрабатывается за 4 мс и отклоняется правилом complexity: его реальная сложность 25 миллионов.

Это **общий приём** для любых рекурсивных обходов графа с повторяющимися узлами: если результат для узла не зависит от пути, по которому вы в него пришли, его надо запоминать.

### 4.2 Утечка памяти
`fragmentCache` был создан в замыкании правила, то есть **один раз на всю жизнь сервера**, и копил фрагменты всех запросов. Теперь все структуры создаются внутри одной валидации (`ValidationRule` вызывается graphql-js заново для каждого документа). Тест подсчитывает записи во всех `Map`: максимум одна на валидацию.

### 4.3 Обходы complexity
- **Переменные.** `items(first: $n)` с `n = 1000` давало множитель 1. Правило теперь создаётся на каждый запрос и получает переменные (и значения по умолчанию из `query($n: Int = 50)`).
- **Повторные фрагменты.** Фрагмент учитывался один раз на всю операцию, а выполняется он столько раз, сколько упомянут. Теперь каждое упоминание учитывается (стоимость берётся из мемо).
- Заработали опции из README и типов: `listArguments`, `defaultListMultiplier` (по типу поля из схемы: возвращает ли оно список), `introspectionCost`, `maxFieldsPerSelection`, `onComplete`, `createError`.

### 4.4 Семантика глубины
- Фрагменты и inline-фрагменты больше **не добавляют уровень**: это только способ записи, `{ a { ...F } }` и `{ a { b } }` имеют одинаковую глубину.
- Introspection меряется своим лимитом (`maxGraphQLIntrospectionDepthLimit`), который раньше игнорировался. Из-за этого **стандартный introspection-запрос GraphiQL и codegen отклонялся** при настройках по умолчанию.
- `DEFAULT_MAX_GRAPHQL_INTROSPECTION_DEPTH_LIMIT`: 8120 → 20. У стандартного introspection-запроса глубина 14 (я замерил), и лимит 20 оставляет запас, но отсекает злоупотребление `__type { fields { type { fields { ... } } } }`.

> ⚠️ **`maxFieldsPerSelection: 50` теперь работает** (раньше значение было объявлено, но игнорировалось). Если в каком-то проекте есть запрос с более чем 50 полями в одном блоке `{ }`, он начнёт отклоняться. Проверьте самые «широкие» запросы фронтендов или увеличьте лимит в конфиге.

Файл `сomplexity-limit-rule.ts` начинался с **кириллической «с»** и переименован.

### 4.5 Значения по умолчанию подобраны по реальным запросам

Все 443 операции клиентов biotransfer (CRM, приложения водителя и клиента) прогнаны через правила 2.11:

| Метрика | Результат |
|---------|-----------|
| Глубина | максимум 10 (у 1 операции), у 95% не больше 7 |
| Сложность с реальными размерами страниц | медиана 25; самые тяжёлые: диалог рабочих часов CRM 13 245 (`first: 10`), история смен водителя до 41 000 (все страницы по 30), адреса CRM 179 983 (`first: 9999`) |
| Ширина | максимум 21 поле в блоке (лимит 50) |

**Почему 5000 больше не годится.** В 2.10 переменные не учитывались (`first: $n` давал множитель 1), поэтому 5000 почти никогда не достигалось, и лимит казался подходящим. При честном подсчёте он отклонял бы обычные запросы CRM. Поэтому prime и поставил `maxComplexity: 50000000`: это фактически выключенный лимит.

**Новые значения:**
- `maxGraphQLDepthLimit`: 10 → **20**. Это значение все проекты (biotransfer, prime, commerce, crm) уже задавали сами. С 2.11 фрагменты не добавляют уровень, так что запас двукратный.
- `maxComplexity`: 5000 → **50 000**. Пропускает реальные операции и отклоняет `items(first: 1000) { items(first: 1000) { id } }` (2 001 000).

**Ещё два обхода закрыты:**
- `last` не считался аргументом размера: `items(last: 100000)` стоил 1;
- если аргумент размера не передан, не учитывалось значение по умолчанию из схемы (`items(first: Int = 1000)`).

**Что сделать в проектах.** Запрос адресов CRM с `first: 9999` (179 983) отклонится и при 50 000. Это осознанно: такой запрос возвращает всю таблицу. Варианты: пагинация или поиск в CRM, либо отдельный `maxComplexity` для маршрута CRM. В prime `maxComplexity: 50000000` стоит заменить на значение, подобранное через `onComplete`.

## 5. fieldsWrapper

| Было | Почему | Стало |
|------|--------|-------|
| Поля без резолвера после обёртки возвращали `null` | В fallback шёл исходный `resolve`, а он `undefined` | Используется `defaultFieldResolver` из graphql-js: он читает `source[field]` и вызывает это значение, если оно функция |
| `wrapWithoutResolvers: false` отключал обёртку **всех** полей | Условие не смотрело, есть ли у поля резолвер | Пропускаются только поля без резолвера |
| Каждое поле превращалось в Promise | Обёртка была `async` | Синхронная обёртка вызывает резолвер синхронно |

Почему последнее важно: graphql-js для синхронных значений идёт быстрым путём, а для Promise создаёт объекты и ставит их в очередь микрозадач. Список из 100 объектов по 5 полей — это 500 лишних Promise на запрос. Бенчмарк с `fieldsWrapper`: **1874 → 3934 запросов в секунду**.

## 6. Разбор тела запроса

- Невалидный JSON раньше **молча** превращался в `{}`, и клиент получал непонятное «The request is empty». Теперь ошибка сообщает, что тело не является валидным JSON.
- `variables` обязаны быть объектом: массивы, числа и JSON-строки не-объектов отклоняются. Batch-запросы (массив) отклоняются явно.
- **`pipe` против `pipeline` против «ничего не уничтожать».** Это тонкое место потоков Node:
  - `a.pipe(b)` **не передаёт ошибки**: если `request` оборвался или gzip битый, промис чтения мог не завершиться никогда;
  - `stream.pipeline(a, b)` передаёт ошибки, но при ошибке **уничтожает все потоки**, включая `request`, а с ним и сокет. Клиент вместо ответа 400 получил бы разрыв соединения;
  - поэтому чтение тела сделано вручную: ошибки и `request`, и декодера подписаны явно, при ошибке поток отсоединяется (`unpipe`) и ставится на паузу, а сокет остаётся живым для ответа.
- Размер тела проверяется и по заголовку `content-length`, и по фактически прочитанным байтам: заголовка может не быть, или он может врать. Отдельно проверяется размер после распаковки (защита от gzip-бомб). Добавлен `br` (brotli).
- Сообщение `Got «[object Object]»` исправлено, `Content-Type` сравнивается точно и без учёта регистра.

## 7. Скаляры

| Скаляр | Изменение | Почему |
|--------|-----------|--------|
| `DateTime` вход | Только `YYYY-MM-DDTHH:mm:ss(.sss)Z` и реальные даты | Восстановлен **ваш** замысел из коммита «Security: fixed scalar date issue», который потерялся при рефакторинге (тесты его ещё помнили). Строка без часового пояса неоднозначна, а `new Date('1')` превращается в 2001 год |
| `DateTime` timestamp | Принимаются любые миллисекунды, отклоняются только значения `|x| < 1e11` | Раньше отклонялось всё до 09.09.2001 (дни рождения!). Порог 1e11 мс — это 1973 год, а 1e11 секунд — 5138 год, поэтому секунды, переданные по ошибке, всё равно ловятся |
| `DateTime` выход | Без изменений: любая валидная дата | Резолверы отдают значения из БД в разных форматах, ломать ответы нельзя |
| `Money` | Только строки из десятичных цифр | `BigInt('')` = `0n`, а `BigInt('0x10')` = `16n`, что для денег недопустимо |
| `Time` | `00:00`–`23:59:59` и `24:00`; вывод всегда `HH:MM:SS` | `24:59` проходило; `9:05` возвращалось как `9:05`, а `09:05` как `09:05:00` |
| `URL` | Запрещены `javascript:` и `vbscript:` | Такой URL валиден, но, отрисованный ссылкой на фронте, даёт XSS |
| `BigInt` | Ошибки — `GraphQLError`, не больше 100 цифр | Раньше падал `SyntaxError`/`TypeError` |
| `JSONObject` | Литерал обязан быть объектом | |

## 8. Новые опции безопасности

Все опции **необязательные** и по умолчанию сохраняют прежнее поведение, чтобы проекты не сломались при обновлении. Включать их стоит осознанно.

| Опция | Что делает | Почему не включена по умолчанию |
|-------|-----------|--------------------------------|
| `maskErrors: true` | Ошибки, которые **не** `GraphQLError` (БД, драйверы, обычный `Error`), уходят клиенту как `Internal server error` | Проекты наверняка показывают пользователю `throw new Error('Пользователь не найден')`. Сначала такие места нужно перевести на `GraphQLError` |
| `onError(err)` | Получает оригинал каждой ошибки до маскирования | Без маскирования он тоже полезен для логов |
| `csrfPrevention: true` | GET и multipart-запросы требуют заголовок `x-requested-with` / `apollo-require-preflight` / … | Фронтенды должны начать слать заголовок. Это **важно, если авторизация на cookie**: браузер отправляет multipart на чужой сайт без preflight вместе с cookie |
| `persistedQueriesOnly: true` | Принимаются только запросы из `persistedQueriesMap` | Нужен готовый allowlist |
| `introspection: false` | Отключает `__schema`/`__type` | GraphiQL и codegen в dev-режиме им пользуются |
| `limits.maxGraphQLTokens` | Парсер останавливается на огромных документах (по умолчанию 10 000 токенов) | Уже включено |

**Исправления без опций:**
- `extensions` (счётчик запросов, время старта) теперь возвращаются **только в `debug`**. Так и было задокументировано, но код отдавал их всегда.
- Ошибки резолверов проходят через форматтер. Раньше они уходили как сырые объекты, мимо `debug`.

**Рекомендуемая конфигурация для прода:**
```ts
graphqlHTTPFactory({
  schema,
  debug: false,
  maskErrors: true,                          // после перевода «пользовательских» ошибок на GraphQLError
  onError: error => logger.error(error),
  csrfPrevention: true,                      // если авторизация на cookie
  introspection: process.env.NODE_ENV !== 'production',
  middleware: [/* ... */],
});
```

Так бросается ошибка, которую клиент **должен** увидеть:
```ts
import { GraphQLError } from 'graphql';
throw new GraphQLError('Пользователь не найден', { extensions: { code: 'NOT_FOUND' } });
```

## 9. Производительность

**Кэш документов** (`src/utils/lru-cache.ts`). Результат `parse()` и проверки стандартными правилами graphql-js (около 30 правил) зависит **только от текста запроса**, а клиенты шлют одни и те же тексты тысячи раз. Этот результат теперь кэшируется.

**LRU** (least recently used) — кэш, который при переполнении выбрасывает то, к чему дольше всего не обращались. Реализован на `Map`, потому что `Map` хранит порядок вставки: при каждом чтении ключ переставляется в конец, а вытесняется первый.

Кэш ограничен **дважды**: по числу записей (1000) и по суммарной длине текстов (2 МБ). Ограничения только по числу записей недостаточно: клиент может прислать 1000 разных запросов по мегабайту. Правила depth, complexity (зависят от переменных) и правила из middleware выполняются на каждом запросе; теперь они линейные и дешёвые.

**Бенчмарк** (один процесс, запрос со списком из 100 объектов по 5 полей, 20 000 запросов):

| | 2.10.6 | 2.11.0 | |
|---|---|---|---|
| без fieldsWrapper | 2 915 req/s | 4 049 req/s | +39% |
| с fieldsWrapper | 1 874 req/s | 3 934 req/s | +110% |

## 13. Прогресс загрузки файлов

Короткий ответ: **да, это возможно, и делается это на клиенте.** Сервер для этого ничего специального делать не должен.

### Почему на клиенте
Прогресс **отправки** знает только тот, кто отправляет: браузер видит, сколько байт ушло в сеть. Сервер узнаёт о байтах позже, и, главное, ответ на запрос он может прислать только после того, как запрос получен целиком. Поэтому передать прогресс «в том же запросе» нельзя.

### Клиент: `XMLHttpRequest.upload.onprogress`
`fetch()` в браузерах **не умеет** сообщать о прогрессе отправки. Это давнее ограничение спецификации, поэтому используется `XMLHttpRequest`:

```ts
type Progress = { loaded: number; total: number; percent: number };

/**
 * Sends a GraphQL multipart request and reports upload progress.
 */
export function uploadWithProgress(
  url: string,
  query: string,
  files: File[],
  onProgress: (p: Progress) => void,
): Promise<unknown> {
  const form = new FormData();
  // 1. operations: null placeholders instead of files
  form.append('operations', JSON.stringify({ query, variables: { files: files.map(() => null) } }));
  // 2. map: which file goes where
  form.append('map', JSON.stringify(Object.fromEntries(files.map((_, i) => [i, [`variables.files.${i}`]]))));
  // 3. files: the part name is the key from map
  files.forEach((file, i) => form.append(String(i), file, file.name));

  return new Promise((resolve, reject) => {
    const xhr = new XMLHttpRequest();
    xhr.open('POST', url);
    xhr.withCredentials = true;                              // если авторизация на cookie
    xhr.setRequestHeader('apollo-require-preflight', 'true'); // для csrfPrevention
    // Content-Type НЕ ставим: браузер сам добавит multipart/form-data с boundary

    xhr.upload.onprogress = event => {
      if (event.lengthComputable) {
        onProgress({ loaded: event.loaded, total: event.total, percent: Math.round((event.loaded / event.total) * 100) });
      }
    };

    xhr.onload = () => {
      try {
        resolve(JSON.parse(xhr.responseText));
      } catch (err) {
        reject(err);
      }
    };
    xhr.onerror = () => reject(new Error('Network error'));
    xhr.onabort = () => reject(new Error('Upload aborted'));

    xhr.send(form);
  });
}

// использование
await uploadWithProgress(
  '/graphql',
  'mutation($files: [FileUpload!]!) { uploadFiles(filesList: $files) { location } }',
  Array.from(input.files),
  ({ percent }) => (progressBar.value = percent),
);
```

Отменить загрузку можно через `xhr.abort()`. Новый парсер корректно обработает обрыв: удалит временные файлы и вернёт ошибку, ничего не зависнет.

**Если на фронте Apollo Client** с `apollo-upload-client`, ему можно передать свою `fetch`-функцию на базе `XMLHttpRequest`, которая вызывает `onProgress` и возвращает `Response`. Это известный приём, и под него есть готовые небольшие обёртки.

**Важный нюанс:** 100% прогресса отправки означает «байты ушли», но не «сервер обработал». После 100% показывайте состояние «Обработка…» до прихода ответа: ядро ещё дописывает файлы на диск, а резолвер, например, загружает их в S3.

### Сервер: когда прогресс нужен и там
Серверный прогресс нужен, если **обработка** после загрузки долгая: конвертация видео, распознавание документов. Тогда схема такая:

1. клиент генерирует `uploadId` и передаёт его в переменных мутации;
2. резолвер сообщает о ходе обработки в канал, привязанный к `uploadId`: GraphQL subscription, SSE или Redis pub/sub;
3. клиент параллельно слушает этот канал.

Скелет резолвера, который считает прочитанные байты файла (это и есть серверный «прогресс приёма и обработки»):
```ts
resolve: async (_parent, { file, uploadId }: { file: UploadedFile; uploadId: string }) => {
  const { createReadStream, fileSize } = await file;   // fileSize известен: файл уже на диске
  let processed = 0;

  for await (const chunk of createReadStream()) {
    processed += chunk.length;
    await processChunk(chunk);                         // ваша обработка
    progressBus.publish(uploadId, { processed, total: fileSize });  // SSE / subscription / Redis
  }

  return { ok: true };
}
```

Прогресс самой сетевой передачи на сервере можно было бы получить, считая байты в `request.on('data')` и сравнивая их с `content-length`. Но клиент и так знает это точнее и без лишнего канала связи, поэтому для полосы загрузки в интерфейсе правильный путь — клиентский.
